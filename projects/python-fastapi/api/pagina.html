A parte do RAG que decide a qualidade

Quase toda conversa sobre RAG gira em torno do modelo de linguagem. Mas o modelo só responde com o que recebe: se a recuperação trouxer o trecho errado, nenhum modelo salva. Esta página é a etapa que acontece antes — e ela mostra não só o resultado, mas por que cada trecho venceu.

O que este projeto não esconde

BM25 é lexical. Ele pontua por termo raro e saturação de frequência, não por significado. Pergunte usando uma palavra que os textos não usam — “cartão” em vez de “PIX”, “multi-tenant” em vez de “inquilino” — e a busca não encontra. A página avisa exatamente quais termos ficaram de fora.

É aí que entram os embeddings. Eles transformam a pergunta e os trechos em vetores onde “cartão” e “PIX” ficam próximos por significado. A peça que muda é só o ranqueamento; fatiamento, índice e citação continuam iguais. Não coloquei embeddings aqui porque exigiriam uma chave de API paga, e uma demo de portfólio não deveria depender de fatura.

O fatiamento é a decisão mais subestimada. Pedaço grande demais dilui o assunto e traz ruído; pequeno demais perde o contexto que dava sentido à frase. Aqui o corte é por seção, respeitando a estrutura que o autor já criou — em vez de partir a cada N caracteres, que é o padrão preguiçoso.

Citar a fonte não é enfeite. Em texto jurídico ou financeiro, resposta sem origem não serve: alguém precisa conferir antes de assinar. Por isso cada trecho aqui vem com documento, seção e a lista de termos que o fizeram vencer.

A API está aberta: /api/buscar?q=pix e /api/docs com o OpenAPI gerado pelo FastAPI.
