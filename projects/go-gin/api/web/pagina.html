“Dados inválidos” não é mensagem de erro

Mande um produto com campo errado e veja o que volta: qual campo, qual regra, e o que fazer — uma frase por problema, todos de uma vez. É a diferença entre uma API que dá para consumir e uma que obriga a adivinhar. E a resposta ainda traz a cadeia de middleware que a requisição atravessou.

      As regras, declaradas no próprio tipo

      Em Go a validação mora na struct tag, ao lado do campo. Não há esquema separado para sair de sincronia com o modelo. 

      type Produto struct {
    Nome      string  `binding:"required,min=3,max=80"`
    SKU       string  `binding:"required,alphanum,len=8"`
    Preco     float64 `binding:"required,gt=0,lte=1000000"`
    Estoque   int     `binding:"gte=0"`
    Categoria string  `binding:"required,oneof=servico produto assinatura"`
    Email     string  `binding:"required,email"`
}

      O validator devolve um erro por campo, mas a mensagem crua dele é ilegível: Key: 'Produto.SKU' Error:Field validation for 'SKU' failed on the 'len' tag. A função traduzir transforma isso em “sku: precisa ter exatamente 8 caracteres”. São trinta linhas que mudam a experiência de quem integra.

      O botão amarelo dispara um panic de propósito. Sem o middleware de recuperação, o cliente receberia uma resposta vazia, sem pista nenhuma. Com ele, volta um 500 explicando o que aconteceu — e o processo continua de pé.

      Uma honestidade sobre o limite: o rate limit aqui é só um selo na cadeia. Em função serverless o estado não sobrevive entre instâncias, então limite de verdade mora no Redis ou na borda. Deixar uma versão em memória que “funciona” seria mentira — e mentira que só aparece em produção, sob carga.
